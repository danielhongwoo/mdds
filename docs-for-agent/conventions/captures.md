# 캡처 규약

[규약 목록](README.md)

벤더 DDS끼리 통신시켜 잡은 패킷 캡처는 교재의 lab에서 독자가 열어 보는 관찰 자료이고, 이후 chapter에서 파서와 상태 머신을 검증하는 정답 데이터다.

## 위치와 파일
- `captures/<누가-누구>/` 아래에 (예: `cyclone-fastdds/`, 나중에 `mdds-cyclone/`) 시나리오마다 `<시나리오>.pcap` (구독자 컨테이너 `eth0`), `<시나리오>.pub.log`, `<시나리오>.sub.log` (양쪽 stdout/stderr)를 둔다. 같은 디렉터리의 `README.md`가 설명이다.
- 캡처는 스크립트로만 만든다 (예: [docker/capture-shape-scenario.ts](../../docker/capture-shape-scenario.ts)). 누구나 같은 명령으로 다시 만들 수 있어야 한다. 기존 파일은 명시적으로 덮어쓸 때만 바꾼다 (`--force`).

**결정: 디렉터리 이름은 `captures`다.**
- 왜: 내용이 전부 캡처와 그 로그다. 컨테이너 안 마운트 경로 `/captures`와 이름이 같다.
- 버린 대안: `fixtures`. 테스트 준비 코드 (pytest fixture, rstest `#[fixture]`)와 이름이 겹쳐 헷갈린다.

**결정: 캡처는 저장소 루트의 `captures/`에 둔다.**
- 왜: 테스트 코드가 아니라 기록한 관찰 자료다. 같은 캡처를 여러 lab과 chapter가 함께 쓴다 (`rel-cyclone-pub`은 Lab 3-1, 3-2, 4-1과 chapter 7, 10, 11의 정답 바이트 테스트).
- 버린 대안: `tests/captures/`. 관찰 자료가 테스트 디렉터리 아래에 있어 어색하다. `labs/<lab 이름>/`. 캡처와 lab이 일대일이 아니라 어느 lab에 둘지 정할 수 없고, lab 구성이 바뀔 때마다 캡처와 테스트 경로를 옮겨야 한다.

## 크기
**결정: 파일 하나가 10MB를 넘으면 필요한 프레임만 `editcap`으로 잘라 저장한다.** 예: `editcap -r in.pcap out.pcap 1-500`. 자른 사실과 범위, 원래 명령은 README에 적는다.
- 왜: pcap은 바이너리라 git이 변경분만 저장하지 못한다. 커밋한 판마다 히스토리에 통째로 남고, 다시 캡처해 덮어써도 옛 판은 지워지지 않는다. GitHub은 50MB부터 경고하고 100MB를 넘으면 push를 거부한다.
- 10MB 아래는 원본 그대로 둔다. 잘라 낸 파일은 다시 만들 때 같은 범위를 고르기 어렵다.

## README 형식
- 공통 조건: 벤더 버전과 빌드 소스 커밋, 주소, 캡처한 위치, 다시 만드는 명령.
- 파일 표: 시나리오마다 한 줄 (무엇을, 누가 발행, 어디서 캡처).
- 시나리오마다:
  - 실행 명령 (양쪽).
  - 흐름: 프레임 묶음별 개수 (사용자 데이터, 디스커버리, IGMP 등)와 Mermaid 시퀀스 다이어그램 ([markdown.md](markdown.md#다이어그램)).
  - 질문: 캡처에서 보이지만 답하지 않은 것. 줄 끝에 답을 찾을 chapter를 붙인다 (`-> chapter 10`).
  - 필요하면 요약 표 (seq 범위, 로그 샘플 수)와 Wireshark 필터.
- 벤더 차이 표: 캡처에서 확인한 두 벤더의 다른 점.

다이어그램 표기:
- 메시지마다 앞에 `프레임 번호 (시각)`을 붙인다. 시각은 캡처 시작 기준 초.
- 실선 (`->>`)은 유니캐스트, 점선 (`-->>`)은 멀티캐스트.
- 필드 값은 그대로 적는다. `HB a-b`는 HEARTBEAT의 firstAvailableSeqNumber a, lastSeqNumber b. `ACKNACK b/n:bits`는 readerSNState의 bitmapBase/numBits:bitmap (RTPS 2.5 Sec. 9.4.2.6의 표기).

**결정: 캡처 메모는 관찰과 질문까지만 적는다.** 다이어그램에는 메시지 이름, 방향, 필드 값만 쓰고 "매칭", "요청", "보낼 것 없음" 같은 해석은 쓰지 않는다. 해석이 필요한 것은 "질문"에 적고, 이미 세운 가설은 답을 찾을 chapter의 저자 노트 (`docs-for-agent/notes/`) "확인할 것"에 `[추정]`으로 둔다.
- 왜: 캡처는 그 주제의 규격을 읽기 전에 먼저 본다. 이때 쓴 해석은 맞는지 확인할 수 없다. 해석을 캡처 메모에 쓰면 저자 노트, book의 chapter와 같은 설명이 두 곳에 생긴다. 질문 목록은 그 chapter에서 풀 숙제가 된다.
- 버린 대안: 메커니즘 설명까지 적기. 캡처를 막 본 시점이라 설명이 쉽게 나오지만, 규격으로 확인하지 않은 추정이 사실처럼 남는다.
